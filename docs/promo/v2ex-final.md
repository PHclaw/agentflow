## 正文

接了个私活，客户想把内部的产品手册、报价单做成能问答的助手。

我本来打算上 Dify，聊了两轮发现两件事过不去：一是他们 IT 不让数据出门，SaaS 一律免谈；二是服务器只有一台 2C4G 的云主机，还要跟别的服务挤。

于是就自己写了一个，叫 AgentFlow，现在开源了。

简单说：填几行提示词、拖几个节点，把「大模型 + 自己的文档 + 一堆小工具」拼成一个能干活的助手。一条 docker compose 起在自己的机器上。

技术上的几个选择，可能有人感兴趣：

默认用 SQLite，不是 PostgreSQL。整个项目起来就两个容器（后端 + nginx），数据落在一个 ./data/agentflow.db 文件里，down 掉不会丢，复制这个文件就是备份。真要扛量了再切 PostgreSQL，代码不用动。

向量检索走 chromadb，embedding 端点独立配置，可以指向本地 Ollama。这点我坚持了很久：不想让「换个模型」变成「重搭一遍」。

工作流引擎是自己写的，没用 LangGraph。需求就六类节点（触发器 / LLM / 知识库 / 工具 / 条件 / 回复），引框架反而多一层调试成本。自研的好处是节点级执行状态能实时回传，前端画布上的节点会一个个亮起来。

踩过的坑，都写在 README 里了：

Docker 镜像里不能塞 sentence-transformers（要 2GB），所以 EMBEDDING_BASE_URL 必须填，留空会静默失败——表现为知识库能建但一条都检索不出来，很难查。

.env 里的 CORS_ORIGINS 一旦设置就会整体覆盖默认值。加一个来源得把所有来源写全，只写新的那个，其他全 403。

DATABASE_URL 留成空串会被当成真实连接串，后端直接起不来。不需要改就整行注释掉，别留空。

现在有什么：

17 个页面——落地页、控制台、Agent 配置、工作流画布、对话、对话记录、知识库、Skill 广场、模板市场、设置、管理后台。

26 个技能目录，Excel / PPT / PDF / 学术检索 / 会议纪要 / 统计分析这些，加一个带 SKILL.md 的文件夹就多一个能力，不用改代码。

产物是真实文件（xlsx / png / pdf），作为附件回传，图片类直接内联在对话里，不用先下载再看。

顺手用 Capacitor 打了个安卓包，Release 里能直接下。同类项目里带移动端的好像不多。

部署就一条命令：

    git clone https://github.com/PHclaw/agentflow.git
    cd agentflow
    cp .env.example .env      # 至少填 JWT_SECRET_KEY
    docker compose up -d --build

打开 http://服务器IP:3000 就是完整界面。也可以先不装，demo 在这儿：http://159.75.21.251:3000 （需要邮箱注册收验证码，站点是 http，浏览器提示不安全属正常）。

想听听大家的意见：

你们公司如果要私有化部署这类东西，卡点一般在哪？是合规、运维成本，还是效果不稳定？

另外这套现在是「先能跑」的状态，并发和权限都还很朴素。下一步该补哪块，我有点拿不准。

源码和 demo 都在这儿，觉得有用给个 star 就是最大的支持：

## 评论区回复话术（提前备好，别现场编）

### 被问「和 Dify 什么区别」

> 功能面 Dify 更全，插件市场、观测、多租户都比我这个成熟，这点不用绕。
>
> 差别在形态：Dify 起步要 PG + Redis + worker，四五个容器；我这个默认两个容器、一个 SQLite 文件，一台 2C4G 就能跑。
>
> 所以我的适用场景很窄——客户不让数据出门、又没有专职运维。功能要求多的场景，我建议直接用 Dify。

### 被问「和 WorkBuddy 什么区别」

> 不是一个形态，互相替代不了。
>
> WorkBuddy 是桌面客户端，装在每个人电脑上，处理本机文件很顺；我这是服务端，一台机器，团队用浏览器访问。
>
> 差别在这几处：知识库我这天然共享（一套库所有人可检索），它是各自本地；权限我这有管理员后台，它企业版统一管控；扩展方式我这加一个目录就是新技能、还能直接改源码，它是内置技能 + 连接器。
>
> 所以：想要"每个人电脑上有个助手"，桌面端更合适；想要"团队一套系统、知识库共享、有人管权限"，才是我这个。

### 被问「这不就是个套壳」

> 前端 React + ReactFlow，后端 FastAPI + SQLAlchemy async，工作流引擎是自己写的（`backend/app/services/workflow_runtime.py`，拓扑排序 + 分支选择，没用 LangGraph），向量检索走 chromadb。代码都在仓库里，可以随便看。

### 被问「为什么不用 LangGraph / 现成框架」

> 需求就六类节点，LangGraph 的表达能力过剩，多一层抽象就多一层调试成本。自研的好处是节点级执行状态能实时回传——前端画布上的节点会一个个亮起来。

### 被问「商用可以吗」

> 代码 Apache-2.0，允许商用。但 `skills/` 下的技能是各社区的，许可各不相同（Apache-2.0 / MIT / 无声明 / 保留所有权利），要商用分发建议先看 `THIRD_PARTY_NOTICES.md`，或者把不需要的技能目录删掉。

### 被问「没看到 XX 功能」

> 先确认下版本：README 里的界面截图对应的是当前 master。如果功能确实没了，直接开 issue，我这边优先修文档与代码不一致的问题——被指出过几次，这块我盯得比较紧。
