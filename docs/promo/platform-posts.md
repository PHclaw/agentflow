## 一、V2EX（分享创造节点）

**标题**：一个人做了个能装进自己机房的 AI Agent 平台，还顺手做了安卓端

**正文**：

前段时间接了个私活，客户想把内部的产品手册、报价单做成能问答的助手。我本来打算上 Dify，聊了两轮发现两件事过不去：

1. 他们的 IT 不让数据出门，SaaS 一律免谈；
2. 服务器只有一台 2C4G 的云主机，还要跟别的服务共用。

于是就自己写了一个，叫 AgentFlow，现在开源了。简单说：拖几个节点、填几行提示词，就能把「大模型 + 自己的文档 + 工具箱」拼成一个能干活的助手。

**技术上的几个选择**

- 前端 React 18 + ReactFlow（工作流画布），后端 FastAPI + SQLAlchemy 2.0 async
- **默认 SQLite**，一个文件就是全部数据，`docker compose down` 也不会丢。要扛量再切 PostgreSQL + pgvector，代码不用动
- 向量检索用 chromadb，embedding 端点**独立配置**，可以指向 Ollama
- 工作流引擎是自己写的（`workflow_runtime.py`），没用 LangGraph —— 需求只有六类节点，引框架反而多一层调试

**踩过的坑，写在 README 里了**

- Docker 镜像里不能塞 sentence-transformers（要 2GB），所以 `EMBEDDING_BASE_URL` 必须填，留空会静默失败
- `DATABASE_URL` 留成空串会被当成真实连接串，后端直接起不来，得整行注释掉
- `.env` 里的 `CORS_ORIGINS` 一旦设置就会**整体覆盖**默认值，加一个来源就得全写一遍

**现在有什么**

17 个页面：落地页、控制台、Agent 配置、工作流画布、对话、对话记录、知识库、Skill 广场、模板市场、设置、管理后台。
26 个技能目录（Excel / PPT / PDF / 学术检索 / 会议纪要 / 统计分析等），放一个带 `SKILL.md` 的目录就多一个能力。
产物是真实文件（xlsx / png / pdf），作为附件回传，图片类直接内联在对话里。

顺手用 Capacitor 打了个安卓包，在 Release 里能直接下——同类项目里带移动端的好像不多。

**部署就一条命令**

```bash
git clone https://github.com/PHclaw/agentflow.git
cd agentflow
cp .env.example .env      # 至少填 JWT_SECRET_KEY
docker compose up -d --build
```

两个容器：backend + nginx。

**想听听大家的意见**

- 你们公司如果要私有化部署这类东西，卡点一般在哪？（合规 / 运维成本 / 效果不稳定）
- 现在这套是「先能跑」，并发和权限都还很朴素，下一步该补哪块？

Demo 和源码都在这儿，觉得有用给个 star 就是最大的支持：
https://github.com/PHclaw/agentflow

> 演示站需要邮箱注册（会发验证码），不想留真实邮箱的话临时邮箱也能过。

## 二、掘金（技术向，偏实现）

**标题**：用 FastAPI + ReactFlow + SQLite 搭一个能出 PPT 的 AI Agent 平台，我做了什么取舍

**正文骨架**：

### 为什么不用现成方案

（三句话：数据不出内网 / 一台 2C4G / 要能交付文件而不是只回文字）

### 一、为什么默认 SQLite，而不是 PostgreSQL

- 对比：Dify 起步要 PG + Redis + worker，四五個容器
- 取舍：单机场景下 SQLite 的写并发够用，WAL 模式下读性能也不差
- 代价：真要迁移，SQLAlchemy 层已经抽象好，改 `DATABASE_URL` 即可；但**向量检索必须换 pgvector**，SQLite 没有等价物
- 落地：`docker compose` 默认两个容器，`--profile postgres` 才起 PG

### 二、工作流引擎为什么自己写

- 只有六类节点（触发器 / LLM / 知识库 / 工具 / 条件 / 回复），LangGraph 的表达能力过剩
- 自研引擎可以做两件事：节点级执行状态实时回传（前端画布能逐节点点亮）、超时与重试策略按节点配置
- 代价：没有社区生态，复杂编排能力要自己补

### 三、流式对话的落地细节

- 不用 `EventSource`，因为它不能自定义 `Authorization` 头
- 改用 `fetch` + `ReadableStream`，自己按 `\n\n` 分帧（一次 read 可能只拿到半帧，必须用 buffer 累积）
- 工具调用提示「正在调用工具」同屏只留一条，避免刷屏

### 四、产物怎么回传给用户

- 生成的文件写到工作目录，接口以 blob 返回
- 图片类产物在对话里内联渲染（`URL.createObjectURL`），组件卸载时 revoke，避免内存泄漏
- 移动端（Capacitor）里 `a[download]` 对 blob 无效，得走 Filesystem + Share —— 这个坑踩了很久

### 五、开放的问题

（并发、任务队列、权限模型）

结尾放仓库链接 + 一句"欢迎拍砖"。

## 三、知乎（选型向，偏决策）

**标题**：中小企业想私有化部署 AI Agent，除了 Dify 还有什么选择？

**正文骨架**：

开头先给判断维度（不吹自己）：

1. 部署成本：几个容器、要不要 PG/Redis、一台 4G 云主机够不够
2. 数据边界：数据库在哪、模型调用是否出网
3. 能不能交付：只回文本，还是能出表格/PPT/PDF
4. 扩展方式：插件市场，还是自己写
5. 团队门槛：运维要不要专职

然后逐条对比 Dify / Coze / 自研 / 本项目（**明确标注"利益相关：我自己写了其中一个"**，这一点必须写，否则被扒出来就是反面案例）。

结尾：如果只是内部知识问答 + 偶尔出报告，一台小机器跑自托管方案就够；如果要对接复杂业务系统和多租户，还是上商业产品或自研。
